# Статистика посещений в админке

Дата: 2026-07-16
Статус: дизайн согласован, план не написан

## Задача

Показать администратору, сколько людей заходит на сайт: визиты и уникальные
посетители за день, с разрезом по источнику перехода и типу устройства.
Без сторонних счётчиков (Метрика/GA) — свой сбор, свои данные.

## Решения и их обоснование

| Решение | Выбрано | Почему не альтернатива |
|---|---|---|
| Что считаем | Визиты + уники за день | Только pageviews не отвечают на «сколько людей»; всё сразу — лишние сущности |
| Разрезы | Источник + устройство | Отвечают на «работает ли реклама» и «нужна ли мобилка». Landing page для SPA бесполезен: 80% будет `/` |
| Сбор | Beacon из SPA | Парс access-лога nginx втрое дороже и считает ботов за людей |
| Граница визита | Окно 30 минут, `localStorage` | Одна вкладка = визит пухнет от перезагрузок; PHP-сессия тащит куки в статистику |
| Админка | Новая страница `/admin/analytics` | Разрезы на дашборд не влезают; дубль «плитки + страница» — двойная работа |
| Хранение | Сырые строки, без чистки | ~180к строк/год ≈ 20 МБ. Агрегаты — решение проблемы, которой нет |

## Ключевое ограничение: `Referer` бесполезен

Заголовок `Referer` на fetch из SPA равен URL текущей страницы сайта, а не тому,
откуда пришёл человек. Настоящий внешний referrer виден только в запросе
HTML-документа, а его обслуживает статический nginx (`docker/nginx/frontend.conf`,
`try_files $uri $uri/ /index.html`) — PHP этот запрос не видит вообще.

Поэтому источник перехода берётся из `document.referrer` в теле beacon'а, а не из
заголовка. Клиент это значение может подделать. Для внутренней статистики
приемлемо; если когда-нибудь понадобится неподделываемый источник — это парс
access-лога, отдельная задача.

`User-Agent` и IP — настоящие заголовки, из запроса.

## Блокер: PHP не видит IP клиента (проверено на стенде)

Контейнерный `docker/nginx/default.conf` содержит:

```
fastcgi_param        HTTP_X_REAL_IP  $remote_addr;
```

`$remote_addr` здесь — адрес того, кто пришёл в контейнер, то есть хостовой
nginx / docker-шлюз, а не посетитель. Эта строка ещё и затирает настоящий
`X-Real-IP`, который хостовой nginx честно проставляет (`docs/nginx-host.conf:41`
и `:50` — `proxy_set_header X-Real-IP $remote_addr`).

Замер на живом стенде (временный роут, откачен):

```
до фикса,  с X-Real-IP: 203.0.113.9  → {"x_real_ip":"172.18.0.1"}   # затёрт
после,     с X-Real-IP: 203.0.113.9  → {"x_real_ip":"203.0.113.9"}  # настоящий
после,     без заголовка             → {"x_real_ip":null}           # падает на REMOTE_ADDR
```

**Фикс: удалить эту строку.** nginx и так передаёт заголовки запроса в FastCGI как
`HTTP_*` автоматически; директива только мешает. Одна строка минус.

Без фикса `visitor_hash` у всех посетителей одинаковый и уники всегда равны 1 —
фича мертва.

### Побочно: этот же баг ломает троттлинг логина (существует сегодня)

`api/helpers/RateLimiter.php:10` берёт `$_SERVER['HTTP_X_REAL_IP']`, и комментарий
на строке 9 говорит ровно то, что задумывал автор: «X-Real-IP выставляется nginx'ом
upstream». Но из-за строки в `default.conf` там всегда докер-шлюз. Значит лимит
«10 попыток за 15 минут» сейчас общий на всех: 10 неудачных логинов кого угодно
блокируют вход всем остальным.

Тот же однострочный фикс чинит и это. Отдельная правка `RateLimiter` не нужна —
его логика уже верна.

### Побочно: порт 8000 открыт наружу

`docker-compose.yml:47` публикует `"8000:80"` на всех интерфейсах, тогда как
postgres и minio привязаны к `127.0.0.1`. То есть API доступен в обход хостового
nginx: мимо TLS, и с возможностью подделать `X-Real-IP` (хостовой nginx его
перезаписывает, а прямой запрос — нет).

Правка: `"127.0.0.1:8000:80"`, как у остальных сервисов. Формально за рамками
фичи, но именно она делает `X-Real-IP` доверенным, поэтому входит сюда.

## Данные

В `docker/postgres/init.sql`:

```sql
CREATE TABLE IF NOT EXISTS visits (
    visit_id     BIGSERIAL PRIMARY KEY,
    visited_at   TIMESTAMP NOT NULL DEFAULT NOW(),
    visitor_hash CHAR(64) NOT NULL,
    source       VARCHAR(20) NOT NULL,
    referer_host VARCHAR(255),
    device       VARCHAR(10) NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_visits_date ON visits (visited_at);
CREATE INDEX IF NOT EXISTS idx_visits_hash ON visits (visitor_hash, visited_at);
```

Второй индекс — под проверку накрутки: она бьёт по `visitor_hash` на каждом
визите, без индекса это seq scan на каждый заход.

`init.sql` применяется только на пустом томе — на проде тот же SQL выполняется
руками. Это отдельный пункт плана, не «оно само».

### Приватность

Сырой IP не хранится нигде, только `visitor_hash`:

```
visitor_hash = sha256(ip . user_agent . VISIT_SALT . date('Y-m-d'))
```

IP по 152-ФЗ — персональные данные. Соль (`VISIT_SALT`, новая env-переменная,
в `.env.example` без значения) не даёт перебрать диапазон IP и восстановить
адрес. Суточная компонента не даёт сшить визиты одного человека между днями.

Размен: уники за неделю такой схемой не считаются, только сумма дневных.
Осознанно — приватность важнее точности недельной цифры.

`referer_host` — только хост (`parse_url(..., PHP_URL_HOST)`), без query: в query
внешних сайтов утекают поисковые запросы и токены.

## Backend

### `POST /api/visit` — публичный, без guard

Новый `api/controllers/VisitController.php`, метод `track()`:

1. `device` — regex `/Mobile|Android|iPhone|iPad/i` по `User-Agent` → `mobile` | `desktop`
2. `source` — по хосту из `document.referrer` (тело запроса):
   - пусто или свой хост → `direct`
   - `yandex|google|bing|mail|duckduckgo` → `search`
   - `vk|t.me|telegram|instagram|youtube` → `social`
   - иначе → `other`
3. `visitor_hash` — по формуле выше
4. Ответ `204`, без тела

Свой хост определяется по `CORS_ORIGIN` — переменная уже есть, новой сущности не надо.

**Защита от накрутки.** Эндпоинт открытый, `curl` в цикле надует счётчик.
Не больше 30 строк на один `visitor_hash` в час — `COUNT(*)` перед вставкой.
`RateLimiter` не переиспользуем: он завязан на таблицу `login_attempts` и своё
окно; счётчик по своей же таблице дешевле, чем обобщать чужой класс под второго
потребителя.

### `GET /api/admin/analytics?days=7`

`AdminSystemController::getAnalytics()` — дашборд и настройки уже там, новый
контроллер ради одного метода не нужен.

**Первой строкой `requireAdmin()`.** Router guard не навешивает — это отдельное
предупреждение в CLAUDE.md, и оно про такие эндпоинты.

`days` — whitelist `[7, 30]`, не подстановка в SQL.

Отдаёт:
```json
{
  "success": true,
  "today": { "visits": 42, "uniques": 31 },
  "chart": { "labels": ["10.07"], "visits": [42], "uniques": [31] },
  "sources": [{ "source": "search", "count": 120 }],
  "devices": [{ "device": "mobile", "count": 200 }]
}
```

Уники — `COUNT(DISTINCT visitor_hash)` с группировкой по `visited_at::date`.
Дни без визитов заполняются нулями в PHP — как уже сделано в `getDashboardStats()`
для 7-дневного графика.

## Frontend

### Beacon

В `src/main.js`, после `app.mount('#app')`:

```
если localStorage.lastVisit пуст или старше 30 минут:
    apiFetch('/visit', { method: 'POST', body: JSON.stringify({ referrer: document.referrer }) })
        .catch(() => {})          // статистика не роняет сайт
    localStorage.lastVisit = Date.now()
```

`apiFetch` подходит: базовый URL и `credentials: 'include'` уже в нём. На `204`
его `res.json().catch(() => ({}))` вернёт `{}` — не ломается.

Метка времени обновляется независимо от исхода запроса: иначе при лежащем API
beacon уйдёт на каждой навигации.

### Страница

`src/views/admin/AnalyticsView.vue` + роут `/admin/analytics` + пункт меню.
Прямой `fetch`, как в остальных админ-вью — стор не заводим, прецедента в проекте нет.
Верстка mobile-first утилитами Tailwind, без scoped-`@media`.

График — тем же способом, что уже используется в `AdminDashboard`.

## Тесты

Проверять то, что реально может сломаться.

`tests/api.test.js`:
- `GET /api/admin/analytics` без админа → 401/403 (забытый guard — известный класс багов в проекте)
- `POST /api/visit` создаёт строку и отвечает 204
- лимит накрутки: 31-й запрос с тем же хешем за час не пишет строку
- `?days=99` не проходит whitelist

`tests/unit/`:
- классификация источника: пусто → `direct`, свой хост → `direct`, `yandex.ru` → `search`, мусор → `other`
- классификация устройства по нескольким реальным `User-Agent`

Каждый тест проверяется откатом фикса — иначе не считается.
Между правкой PHP и прогоном ждать >2 секунд: `opcache.revalidate_freq=2`.

**Проверка фикса с IP** — обязательна, вручную, на стенде: запрос с заголовком
`X-Real-IP: 203.0.113.9` должен привести к строке в `visits` с хешем, отличным от
хеша запроса без заголовка. Автотестом это не ловится: подделка `X-Real-IP` из
теста идёт мимо реального пути хостового nginx.

## Что осознанно не делаем

- Гео (страна/город) — нужна сторонняя база GeoIP, у нас «без сторонних решений»
- Агрегаты и чистка старых строк — до миллионов строк далеко, эндпоинт менять не придётся
- Отслеживание переходов внутри SPA (pageviews) — спрошено «сколько заходов», это визиты
- Уники за неделю/месяц — суточная соль не даёт; только сумма дневных
- Согласие на куки — их тут и нет, `localStorage` под аналитику без персональных данных
